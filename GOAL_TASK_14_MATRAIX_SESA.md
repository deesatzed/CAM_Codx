This is the successor contract for the real MatrAIx/SESA vertical slice named
by `GOAL.md`. It must be run from the recovered CAM_Codx/CAM_CAM feature
worktrees or their verified descendants. It does not reopen the completed
control-plane tasks and does not authorize a broad product integration.

- The exact MatrAIx/SESA repository checkout, source revision(s), target

/goal

OUTCOME: After the product boundary is explicitly accepted, execute the
smallest useful MatrAIx/SESA population-testing slice through CAM_Codx so that
one bounded source-to-outcome chain is reproducible: named source evidence is
assessed, candidates are selected or rejected with provenance, an exact
reviewed plan lands in the authorized target, tests and verification produce a
receipt, and a fresh CAM_Codx recall exposes only the verified active result as
positive reuse evidence. If the target or boundary cannot be authorized, leave
the control plane complete and this slice explicitly blocked with a precise
successor record.

PRODUCT-BOUNDARY CHECKPOINT:

Before any target-repository edit, provider call, paid mining, live import, or
other consequential operation, the contract must record and receive one
meaningful product decision covering all of the following:

1. Exact target repository path, repository owner, and checkout identity.
2. Exact source repository path(s), source owner(s), and immutable Git
   revision(s) to inspect or reuse. Branch names, tags, and moving URLs alone
   are insufficient.
3. MatrAIx/SESA component names and the intended slice outcome. “MatrAIx” or
   “SESA” by itself is not a target path or a permission to copy code.
4. License for every selected source, allowed adaptation/redistribution,
   notices that must be retained, and any component that must remain
   reference-only.
5. Privacy/data boundary: local-only files, prohibited PHI/PII/secrets,
   redaction rules, provider-input rules, retention, and deletion/rollback
   expectations. No credentials, private keys, raw prompts containing secrets,
   or unnecessary personal data may enter packets, logs, providers, or docs.
6. Provider and model policy: whether any provider is permitted; exact model
   or profile, request/time/token limits, maximum cost, retry policy, and local
   fallback. No provider call or paid mining run is implied by this contract.
7. Target mutation and deployment boundary: exact writable paths, test command,
   rollback point, reviewer, and whether the result is a local fixture,
   isolated target change, or deployable product change. Deployment and live
   configuration remain separate approvals.

Until this checkpoint is accepted, the only permitted Task 14 work is local,
read-only discovery, contract editing, and fixture planning.

PROOF OF DONE:

1. **Boundary receipt.** A checked-in Task 14 decision record names the exact
   target and source paths, immutable revisions, owners, licenses, privacy/data
   rules, provider/model/time/cost policy, writable paths, reviewer, rollback,
   and deployment status. Missing or ambiguous fields keep the slice blocked.

2. **Source assessment.** CAM_Codx `assess` produces a redacted, provenance-
   bearing source receipt for each named source. The receipt binds checkout,
   revision, clean/dirty state, file/byte/time bounds, license evidence, and
   the exact CAM/CAM_Codx operation. Read-only assessment does not mine, call a
   provider, alter a corpus, load a model, change a profile, or mutate a
   target.

3. **Candidate ledger.** Every proposed component or method is classified as
   direct precedent, transferable analogy, or new hypothesis. Each row records
   source receipt, license, confidence, limitations, adaptation burden, risk,
   required proof, and state: selected, rejected, deferred, unresolved, or
   hypothetical. Retrieval similarity, a mined row count, or a proposal alone
   cannot make a candidate verified.

4. **Reviewed landing map.** A managed plan binds the exact target identity,
   source revisions, selected candidates, destination paths, allowed file
   changes, tests, rollback, and full plan SHA-256. The plan must state what is
   deliberately not copied and how attribution/license notices are preserved.

5. **Smallest useful slice.** Only after the product-boundary checkpoint and
   reviewed plan are accepted, implement one bounded population-testing or
   mine-to-build slice in the authorized target. Do not copy a donor repository,
   execute arbitrary mined code, add a provider client to CAM_Codx, duplicate
   CAM_CAM runtime logic, or expand into a general MatrAIx/SESA integration.

6. **Verification receipt.** Focused tests and the target's applicable test
   gate run from the reviewed plan. The receipt binds list-form argv, target
   immutable revision, plan ID and digest, exit status, captured bytes, and
   limitations. Failed, partial, synthetic, unrun, stale, or unverified
   evidence remains negative or inconclusive and cannot strengthen positive
   trust.

7. **Source-to-outcome chain.** The durable SWE Run links source receipt,
   candidate decisions, reviewed plan, landing event, verification receipt,
   outcome record, and rollback reference. If a mining or live-import phase is
   used, its bounded corpus/integrity receipt is linked before any build
   selection and its cost/provider receipt is retained.

8. **Fresh recall.** Start a new CAM_Codx assessment after the slice. Only the
   verified active result may appear as positive reuse evidence with its
   provenance and limitations. Rejected, deferred, unresolved, failed,
   synthetic, and hypothetical candidates remain separately visible.

9. **Honest publication.** Update CAM_Codx and CAM_CAM truth docs with exact
   commits, commands, receipts, assumptions, limitations, and rollback notes.
   Label fixture/isolated proof separately from live-product proof. Push only
   the owning repositories' scoped commits; do not publish local databases,
   credentials, private source, or provider output that is not safe to share.

- The exact MatrAIx/SESA target repository is read-only discovery scope until
  the product-boundary checkpoint is accepted; after acceptance, only the
  named target paths and smallest useful slice are writable.
- The canonical implementation roots after consolidation are:
  `/Volumes/WS4TB/waswiki/CAM_Codx` and `/Volumes/WS4TB/waswiki/CAM_CAM`.
  The Downloads worktrees remain recovery references and must not be treated
  as a second runtime or state location.
- Read and reference `GOAL.md`, `IMPLEMENT.md`, `DECISIONS.md`, `PROGRESS.md`,
  `GOAL_KG.md`, `GOAL_LIVE_IMPORT.md`, the Tasks 10-13 release audit, and the
  target's own truth files once its exact checkout is authorized.

NON-GOALS:

- No model/profile promotion, CAM swap, self-enhancement swap, rollback of a
  live profile, production deployment, or live configuration/database change.
- No unbounded repository mining, provider spend, benchmark tournament, or
  automatic model selection.
- No copying or vendoring of MatrAIx, SESA, CAM_CAM, or another donor runtime
  into CAM_Codx.
- No claim that a fixture, synthetic population, retrieval hit, mined count,
  or successful subprocess is real-world accuracy, usefulness, or acceptance.
- No schema migration, public API break, dependency addition, or broad cleanup
  unless the accepted slice proves it necessary and records the decision.

CONSTRAINTS:

- Use test-driven development for behavior changes: add a failing regression,
  make the smallest production change, then run focused and applicable full
  gates.
- Use exact list-form subprocess argv with no shell execution path. Preserve
  secret-argument rejection, bounded files/bytes/time, redacted receipts,
  content-addressed plans, immutable revisions, and single-use approvals.
- Do not run code merely because it was mined, recalled, or selected. Treat
  source as data until the reviewed landing map and target test gate permit the
  exact change.
- Preserve direct reuse, transferred principle, and new hypothesis as distinct
  evidence labels. Retain rejected, deferred, failed, and negative evidence.
- Never run a live import against the canonical `claw.db` during this contract
  without a separate explicit authorization naming source, revision, database,
  snapshot, limits, and rollback/retention plan.
- Keep target, corpus, model-profile, configuration, provider, and deployment
  identities visible before any consequential operation; fail closed on drift.
- Record every safe assumption and command result in `PROGRESS.md`; record
  material architecture, license, evidence, privacy, or UX choices in
  `DECISIONS.md`.

SAFETY / PROVENANCE:

- Resolve and display the exact CAM_Codx checkout, CAM_CAM checkout, wrapper,
  configuration, primary database, target repository, source revisions, and
  model/profile before a mutating or paid phase.
- Preserve source receipts, license notices, attribution, and data-boundary
  decisions for every reused component. Do not expose secrets, credentials,
  private keys, PHI/PII, private source, or unnecessary personal data to
  providers, logs, packets, docs, or subagents.
- Verification hashes and parses one captured byte buffer. A receipt binds the
  exact plan digest and immutable target identity; mutable labels are rejected.
- A provider call, paid mining, target mutation, model/profile promotion,
  deployment, or destructive action requires its own explicit authorization.
  The Task 14 product-boundary checkpoint does not silently authorize those
  operations.
- If source rights, privacy, provider policy, or target ownership are unclear,
  preserve the evidence and stop at discovery rather than guessing.

ITERATION:

1. **Contract discovery.** Inspect only named local paths and available truth
   docs. Resolve target/source identities, ownership, licenses, privacy rules,
   provider policy, and writable paths. Write the boundary receipt. If any
   critical field is unavailable, report Task 14 blocked without editing the
   target.
2. **Read-only assessment.** Run CAM_Codx `assess` and existing CAM_CAM
   primary-only/graph seams against bounded fixture or authorized local sources.
   Capture source and license receipts; prove no target/corpus/profile/config
   identity changed.
3. **Selection and plan.** Build the candidate ledger and landing map. Review
   rejected/deferred/uncertain candidates, adaptation burden, tests, rollback,
   and proof requirements. Produce the digest-bound managed plan.
4. **Product checkpoint.** Pause for the single meaningful decision if the
   exact target, license, privacy, provider, or product scope was not already
   unambiguously authorized. Do not replace this with per-file approvals.
5. **Bounded implementation.** After acceptance, implement only the smallest
   useful slice in the named target. Run focused tests after each batch, then
   applicable full gates. Repair caused failures; record unrelated baselines.
6. **Verify, record, recall.** Execute the reviewed verification packet, record
   the outcome and rollback reference, start a fresh CAM_Codx assessment, and
   prove the positive/negative evidence separation. Synchronize truth docs,
   run `git diff --check`, commit, push, and report exact refs.

STOP:

Pause and report the exact blocker if any of these applies:

- the exact MatrAIx/SESA target or source checkout cannot be identified;
- ownership, license, attribution, privacy, data retention, provider policy,
  or permission to adapt/redistribute is missing or ambiguous;
- credentials, API keys, accounts, or private data access are required and
  unavailable;
- a provider call, paid mining, live import, model/profile change, target
  mutation, destructive action, deployment, or live configuration/database
  change lacks its separate explicit authorization;
- the source is dirty, mutable, out of bounds, or cannot produce an immutable
  provenance receipt;
- required verification cannot run and no safe local, isolated, fixture, or
  read-only alternative can establish the named evidence;
- the same blocker remains after three distinct documented repair strategies;
- continuing would require weakening evidence semantics, hiding negative
  evidence, discarding user changes, or expanding beyond this slice.

Do not stop merely because a test fails, a reviewer finds a defect, a document
needs alignment, or another safe repair iteration is available.

COMPLETE:

Mark this goal complete only when every PROOF OF DONE item is supported by
current command output and inspected artifacts; the accepted boundary receipt,
candidate ledger, reviewed plan, landing, verification, outcome, and fresh
recall are linked; owning commits are pushed; docs match implementation; and
fixture versus live evidence is honestly labeled. If discovery cannot resolve
the boundary, mark the control plane complete and Task 14 blocked, preserve
this contract with the missing fields named, and do not claim a MatrAIx/SESA
vertical slice exists.
