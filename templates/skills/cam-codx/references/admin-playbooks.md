# Administrative Playbooks

Plan one explicit canonical operation and use the capability contract policy.
Do not treat a family name as open-ended authorization.

## Models

Use `models` read-oriented defaults to inspect current selection or a pinned
catalog. Benchmark provider use needs explicit fixtures, metrics, budget, and
approval. Model/profile set, use, select, promote, and rollback are separate
promotion/configuration packets with rollback evidence.

## Self-enhance

1. Inspect the status/threshold route.
2. Prepare a supervised candidate with a small task count and `--skip-swap`.
3. Review its diff, protected files, regression results, and rollback artifact.
4. Reject a failing candidate. Never rewrite failure as improvement.
5. Prepare live swap only through a later, separate approval. Rollback is also
   an explicit live CAM mutation.

## Evolution

Use `evolution` to inspect state before starting or resuming a bounded
champion/challenger cycle. Bind run identity, tasks, models, budget, corpus,
validation, and artifacts. Selection/approval or champion database changes are
promotion/configuration actions, not inspection.

## Doctor

Use `doctor` for CAM identity, capability drift, config/database disagreement,
security, environment, key readiness, or service diagnostics. Some status and
key checks may call configured providers or initialize state; trust the
capability contract rather than the command's friendly name.

Use direct CAM_CAM only for troubleshooting, runtime development, recovery,
or regression isolation when the CAM_Codx layer prevents diagnosis. Return to
CAM_Codx after isolation.

## Setup

Use `setup` to install or repair the wrapper, pinned runtime paths, contract,
and canonical skill. Do not print environment values. Do not delete legacy
skills unless the migration step explicitly creates a recoverable backup and
reports every moved path.
