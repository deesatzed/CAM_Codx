## What This Project Does
**CAM** = "Codebase Learning & Autonomous Workforce" (`claw` package, v0.1.0). A local,
multi-model, repo-intelligence and coding-memory system. It mines reusable engineering
methodologies from source into a local SQLite "brain" (`claw.db`) with provenance and lifecycle,
then uses that brain to plan, build, and verify code changes. Hub-and-spoke:

- **CAM_CAM** — the runtime **engine** (`cam` CLI). Where mining/building/verifying happens.
- **CAM_Codx** — the **program-manager hub**: goal contracts, docs, registries. Consumes CAM
  packets and drives builds via `/goal <CAM_CODEX_GOAL.md>`.

**Tech Stack:** Python ≥3.12, Typer CLI, aiosqlite + sqlite-vec, OpenRouter LLMs.
**Architecture Pattern:** CLI engine + docs/goal hub + generated product repos.

### Step 5 — MINE 2 REPOS (mission item 1)
`cam mine` takes a **directory containing git repos**. Two clean ways to mine exactly 2:

**Option A — put the 2 target repos in one folder, cap at 2:**
```bash
mkdir -p <DRIVE>/CAM/mine_targets
git clone <REPO_URL_1> <DRIVE>/CAM/mine_targets/repo1
git clone <REPO_URL_2> <DRIVE>/CAM/mine_targets/repo2

cd <DRIVE>/CAM/CAM_CAM && source .venv/bin/activate
cam mine <DRIVE>/CAM/mine_targets --scan-only            # preview: no LLM calls
cam mine <DRIVE>/CAM/mine_targets --max-repos 2 --self-assess
```
`--self-assess` classifies new findings against existing knowledge after mining.

**Option B — mine each repo's parent dir one at a time** if they live in different places:
```bash
cam mine <DRIVE>/path/to/parentA --max-repos 1 --self-assess
cam mine <DRIVE>/path/to/parentB --max-repos 1 --self-assess
```
Confirm the brain grew:
```bash
cam stats        # methodology count should be > 2474
```

### Step 6 — GENERATE THE BUILD PACKET (mission item 2 — CAM_CAM engineers it)
`cam create` turns a plain-language outcome into a build task + a **`CAM_CODEX_GOAL.md`** packet
in a build folder. Use `--repo-mode new` for a brand-new project.
```bash
cd <DRIVE>/CAM/CAM_CAM && source .venv/bin/activate
cam create <DRIVE>/CAM/builds/<new-project-name> \
  --repo-mode new \
  --request "Plain-language description of the project to build" \
  --title "<short title>" \
  --priority high \
  --spec "<requirement line 1>" \
  --spec "<requirement line 2>" \
  --check "<acceptance check 1>" \
  --check "<acceptance check 2>" \
  --preflight            # force structured preflight so the contract is scoped before coding
```
This produces the **build folder with all background info**: the new repo scaffold, a
`CAM_CODEX_GOAL.md` build contract, and evidence artifacts — exactly what CAM_Codx consumes.

### Step 7 — CAM_Codx AS AUTONOMOUS PROGRAM MANAGER (mission item 2, cont.)
Two complementary mechanisms — use both:

**(a) CAM_Codx drives the goal contract** (this is the "program manager" role):
From a CAM_Codx checkout / Codex session, point Codex at the packet's contract:
```
/goal <DRIVE>/CAM/builds/<new-project-name>/CAM_CODEX_GOAL.md
```
CAM_Codx reads the contract, recalls proven methods, tracks the checklist, and manages the build
to its acceptance checks. (`docs/QUICKSTART_CODEX.md` → "Continue From A CAM Packet".)

**(b) CAM_CAM runs the autonomous build/verify loop** on the new repo:
```bash
cd <DRIVE>/CAM/CAM_CAM && source .venv/bin/activate
cam enhance <DRIVE>/CAM/builds/<new-project-name> --mode autonomous
```
`enhance` runs the full evaluate → plan → dispatch → **verify** → learn pipeline. `--mode
autonomous` runs without per-step prompts; use `supervised` first if you want gates. Results feed
back into `claw.db`, so the brain learns from the build.

**Division of labor:** CAM_Codx owns the *contract and program management* (what/why/acceptance);
CAM_CAM owns the *engineering execution and verification* (how). The build folder holds all
background so the two coordinate through files, not memory.
